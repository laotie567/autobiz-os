# 新增售前域：需求碎片 → 需求分析 → 售前方案，交付反哺获客

0.3 版本体的交付域只覆盖成交之后（项目 / 里程碑 / 交付物），从"客户甩来模糊需求"到"成交"这一段缺失，而这正是收入的来源。本人工作状态碎片化：需求来自微信、线下 / 电话、飞书会议、抖音私信，需要随手丢进系统，由系统逐步推成方案。

决定：新增售前域（requirement_note / requirement_analysis / proposal / solution_architecture）与 8 个行动，形成闭环：内容获客 → 需求 → 方案 → 成交 → 项目 → 结项沉淀案例 → 回到知识地图；需求经脱敏同时转为选题，反哺获客。

## Consequences

- 本体负责"找"、模型负责"写"：候选痛点 / 案例 / 组件 / 产品由代码检索后编号交给模型，模型只能引用编号；正文中的编号自动替换为名称。
- 方案只能引用已确认知识（proposal_cites 声明 require_verified）；价格与阶段金额由代码按服务产品计算，模型输出阶段金额即判不合格；付款节点永远标注"待本人确认"。
- 适配度只列信号不下结论，筛选闸口由本人判断。
- 闸门：confirm_analysis（分析确认后才能出方案）、accept_proposal、requirement_to_topic。
- 新增"无需预览"（direct）行动类别：只产生草稿的 AI 行动直接执行，把关在后续闸门；带 AI 内容过闸门的行动（需求转选题）用 llm_cache 保证"预览即所得"。
- 方案输出飞书文档（lark-cli）+ 本地 Markdown 留档（proposals/，不入库）；飞书幻灯片尚未接入。
- 模型：需求分析与方案用 deepseek-v4-pro（量小、直接给客户看），脱敏选题用 deepseek-flash。
